# Component boundaries

The root package owns Config, Engine, API, Store, Lifecycle, Registry and BackupAPI. The `snapshot` package owns Artifact, Changes, Manifest and Snapshot. SDK models remain exclusively in `sdk`; its optional NewWithConfiguration constructor accepts the native SDK configuration at that boundary. The CLI composes the library. No service or platform persistence assumptions are imposed. API doubles and HTTP RoundTripper doubles exercise the actual adapter without live traffic.

Flow: discover exportable types → validate selection → initiate once → poll COMPLETE → download → validate every envelope → organize → publish → optional cleanup. A successful export is distinct from cleanup success.

Organization is pure. It requires matching tenant, selected types, nonempty stable identity, positive integer version and an object payload. Unknown fields and signatures survive. JSON keys are sorted using encoding/json; arrays keep source order and numbers use json.Number to avoid float precision loss. Duplicate JSON keys are rejected. Operational timestamps are only in the manifest. This is deterministic JSON, not a cryptographic JSON canonicalization standard; no signatures are regenerated or claimed verified.

IDs become `id-<UTF-8 hex>.json`, a reversible portable encoding that avoids colon substitution and case-fold collisions. Slash, backslash, control characters, dot identities and IDs over 100 bytes fail validation. Tenant/type names use restricted portable identifiers; device names are forbidden. Case-folded path collisions fail closed.

Consumers use Manifest.Artifacts (relative paths, SHA-256), Counts, Types, JobID, Completed and Changes. Artifacts contain the complete original object envelope; top-level download metadata remains operational input, not individual object content. Fetch and Organize may be used independently of filesystem publication.

## Filesystem publication

FileStore stages a complete private generation under `.isc-snapshots/<tenant>-<random>`. It writes and syncs files, directories and the generation parent before atomically renaming a relative symlink at `<output>/<tenant>`. A mkdir lock serializes cooperating publishers per tenant. A crash leaves the previous pointer or a fully staged new generation, plus possibly an orphan generation, temporary pointer or stale lock. Inspect the pointer and manifest before manually removing a stale lock; never remove an active writer's lock. Unreferenced generations remain for recovery; automatic generation garbage collection is intentionally absent. Individual artifacts are 0600 and directories 0700. Unchanged artifacts are hardlinked, retaining inode/mtime. Treat generations as read-only: editing a hardlinked artifact also edits older generations; checksum validation will block the next publication.

Only files listed in the previous manifest are reconciled. Unmanaged regular files are copied; symlinks, special files and collisions fail publication. A filtered export replaces the managed snapshot with exactly the selected types; excluded types from an earlier snapshot appear in Deleted. Previous generations remain on disk. An existing ordinary tenant directory is never adopted or replaced. The reserved manifest.json belongs exclusively to the exporter.

The output root is trusted, private operator-controlled storage; os.Root contains operations beneath it. It must not be concurrently modified by unrelated processes. Generation directories and nested files must not contain symlinks. Use a local POSIX filesystem with atomic symlink rename, directory fsync and hardlink support. Windows, network filesystems and hostile shared roots are unsupported. Rename provides atomic visibility; readers needing consistency across several files must pin a generation using CurrentPath, then read its manifest and artifacts. Re-resolving the tenant symlink for each read can mix generations. Cancellation is checked immediately before the commit point; cancellation racing with rename may still publish. Failure after rename during parent fsync reports an error with a visible complete snapshot whose crash durability is uncertain. The implementation provides atomic visibility plus explicit syncs, not a guarantee against faulty storage hardware. Filesystem and context failures before rename preserve the previous generation.

## Backup lifecycle

BackupManager evaluates all candidates before deletion, with disabled cleanup as default. Age uses a strict older-than boundary; `d` is a fixed 24-hour duration. Keep-latest protects all equally newest successful verified backups, even those without deletion permission. Incomplete, failed, partial, unknown, duplicated and metadata-mismatched records are skipped. A live recheck must match enumeration exactly, and a protected successor must still exist. Audit decisions distinguish retain, skip, would_delete, deleted and delete_failed. No raw API error details are surfaced. Service calls lifecycle only after publication and reports cleanup failure independently.

The SDK-backed lifecycle is intentionally non-destructive because reliable SP-Config/Configuration Hub ownership and conditional deletion semantics are undocumented. Registry persistence uses an exclusive mkdir lock, staged file, fsync and atomic rename, restricted modes, duplicate rejection and explicit tenant filtering. It is a trusted local ledger, not a remote authority. No records are auto-created based on names or inferred ID equality. See API.md for the verified boundary and future integration requirements.


## Native SDK reuse

Connection settings are loaded from local config.json or SAIL_* without the deprecated home-directory fallback; authentication is delegated to the root SailPoint SDK. One root client supplies Beta and V2026 services; the exporter no longer creates parallel per-version configurations or OAuth token sources. The SDK's retryable HTTP client supplies bounded read retries, backoff and Retry-After handling. Engine handles business-level job polling, not HTTP retries. Adapter gating prevents concurrent mutation of SDK token caches; context cancellation can interrupt gate waits/API requests, but cannot interrupt the SDK's separate native token acquisition. The full review, retained exporter responsibilities and upstream constraints are recorded in SDK_REUSE_AUDIT.md and CONFIGURATION.md.

## Independent mapping retrieval

`MappingAPI`, `MappingRequest`, `MappingSnapshot` and `RetrieveMappings` provide a separate library path for read-only Object Mapping retrieval. They do not extend the existing configuration-export API interface. `sdk.Adapter.GetMappings` calls the existing V2026 Configuration Hub client under the same gate and HTTP retry policy; SDK-generated per-version token caches remain native. Raw mapping bytes survive the SDK response-decoding boundary, and storage validation rejects ambiguous or malformed mapping records without interpreting JSONPath.

`MappingFileStore` stages and publishes `mappings.json` plus checksum-bound `provenance.json` into a new independent directory, with restricted permissions, cooperating-writer locking, syncs and atomic rename. Existing bundles are refused. The CLI enforces separation from the configured configuration export tree before authentication and again before publication. No mapping data is inserted into object envelopes or snapshot manifests. The explicit CLI retrieval branch bypasses export/backup/cleanup orchestration. See [MAPPINGS.md](MAPPINGS.md) for the contract and offline differ boundary.
